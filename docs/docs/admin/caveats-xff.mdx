# Client IP Headers

Currently Anubis will always flatten the `X-Forwarded-For` when it contains multiple IP addresses. From right to left, the first IP address that is not in one of the following categories will be set as `X-Forwarded-For` in the request passed to the upstream.

- Private (`XFF_STRIP_PRIVATE`, enabled by default)
- CGNAT (always stripped)
- Link-local Unicast (always stripped)

```
Incoming: X-Forwarded-For: 1.2.3.4, 5.6.7.8, 10.0.0.1
Upstream: X-Forwarded-For: 5.6.7.8
```

This behavior will cause problems if the proxy in front of Anubis is from a public IP, such as Cloudflare, because Anubis will use the Cloudflare IP instead of your client's real IP. You will likely see all requests from your browser being blocked and/or an infinite challenge loop.

```
Incoming: X-Forwarded-For: REAL_CLIENT_IP, CF_IP
Upstream: X-Forwarded-For: CF_IP
```

As a workaround, you should configure your web server to parse an alternative source (such as `CF-Connecting-IP`), or pre-process the incoming `X-Forwarded-For` with your web server to ensure it only contains the real client IP address, then pass it to Anubis as `X-Forwarded-For`.

If you do not control the web server upstream of Anubis, the `custom-real-ip-header` command line flag accepts a header value that Anubis will read the real client IP address from. Anubis will set the `X-Real-IP` header to the IP address found in the custom header.

The `X-Real-IP` header will be automatically inferred from `X-Forwarded-For` if not set, setting it explicitly is not necessary as long as `X-Forwarded-For` contains only the real client IP. However setting it explicitly can eliminate spoofed values if your web server doesn't set this.

See [Cloudflare](environments/cloudflare.mdx) for an example configuration.

## Trusted proxies

The rules above assume that private addresses in `X-Forwarded-For` belong to your own infrastructure. That breaks when your users are on a private network too, for example an office network, a VPN, or other services in the same Kubernetes cluster. A proxy that connects to Anubis from a private address makes it worse:

- With `XFF_STRIP_PRIVATE=true`, the client and the proxy are both removed, so the upstream gets no `X-Forwarded-For` at all and every private client looks the same.
- With `XFF_STRIP_PRIVATE=false`, the proxy is the right-most address left, so every client, public ones included, looks like the proxy.

To fix this, tell Anubis which addresses your proxies connect from with `XFF_TRUSTED_PROXIES` (or `--xff-trusted-proxies`). It takes a comma-separated list of IP addresses and CIDR ranges:

```
XFF_TRUSTED_PROXIES=10.0.0.5,192.168.100.0/24
```

Anubis then reads `X-Forwarded-For` from right to left, starting with the address that connected to it. It skips loopback addresses and anything in the list, and the first address that is left is the client. That address is passed upstream as the only entry in `X-Forwarded-For`, even if it is private, CGNAT or link-local. Everything to its left was written by the client and is ignored. If every address in the chain is trusted, the left-most one is used.

```
Connection from:  10.0.0.5
Incoming:         X-Forwarded-For: 198.51.100.7, 192.168.1.20
Upstream:         X-Forwarded-For: 192.168.1.20
```

If your proxy does not set `X-Real-IP`, Anubis sets it to the same client address. `XFF_STRIP_PRIVATE` has no effect while `XFF_TRUSTED_PROXIES` is set.

Only list the addresses your proxies connect from. Do not list the networks your users are on and avoid listing a whole Kubernetes pod network: anything that connects to Anubis from a trusted address can choose which client address Anubis passes on. Your proxy also has to add to or overwrite `X-Forwarded-For`. If it passes the client's header through unchanged, the client controls the result.
